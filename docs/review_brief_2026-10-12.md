- 배포본(PWA): https://ljh4284-pixel.github.io/JLPT-APP/
- 설계 원본: 저장소의 `PROJECT.md`(설계서), `CLAUDE.md`(작업 규칙), `docs/jlpt_exam_format.md`(JLPT 시험 형식 조사)

## 0. 검토자가 알아야 할 맥락

- 개발자는 1인이며 코딩 경험이 거의 없다. 설계 결정은 개발자가 내리고, 구현은 AI 코딩 도구(Claude Code)가 한다. 따라서 "유지보수 가능성"과 "설명 가능성"이 중요하다.
- 첫 사용자는 개발자 본인(목표: 약 7개월 뒤 JLPT N2). 매일 5~10분 사용이 목표. 하지만 아직 개발자가 앱으로 실제 학습을 꾸준히 해 보지는 않았다(브라우저 자동 점검만 거침).
- 운영 비용 0원 구조가 원칙: 런타임에 서버·DB·AI API를 호출하지 않는다. 모든 계산과 저장은 사용자 기기에서 한다. 음성은 개발 시점에 미리 생성한 mp3 파일이다.
- 검토 요청의 핵심은 §7의 질문 목록이다. 그 외에도 눈에 띄는 문제는 자유롭게 지적해 주기 바란다.

## 1. 전체 프로젝트 계획 (PROJECT.md 요약)

### 1-1. 목표
JLPT 급수별(N5→N1) 어휘를 간격 반복으로 장기 기억에 정착시키는 앱. PWA(웹)로 먼저 완성하고, 안정화 후 Capacitor로 iOS·Android 앱으로 포장해 스토어 출시. 단어장 파일만 바꾸면 다른 언어에도 쓸 수 있는 구조를 지향.

### 1-2. 학습 원리 (우선순위 순, 설계서에 근거 논문 명시)
1. 간격 반복(FSRS 알고리즘)
2. 인출 연습: 답을 보기 전에 반드시 스스로 떠올리게 함
3. 즉시 피드백
4. 복습 혼합: 신규 세션에도 기존 단어 복습을 섞음
5. 학습 방향 전환: 초급은 단어→뜻, 상급은 뜻→단어
6. 짧은 예문 1개만
7. (후순위) 한자 분해, 기억법, 이미지 카드

### 1-3. 문제 유형 (3종만 만든다는 것이 규칙)
| 유형 | 화면 이름 | 형식 | 판정 |
|---|---|---|---|
| A | 뜻 회상 | 표기+읽기 제시 → 뜻을 떠올린 뒤 정답 보기 → 자기평가 4버튼(다시/어려움/보통/쉬움) | 자동 판정 없음 |
| B | 읽기 고르기 | 한자 표기 제시 → 읽기 4지선다. 음성 없음(JLPT 漢字読み 형식). 가나 단어는 뜻 제시 | 선택지 동일성. 오답이면 "다시" 고정 |
| C | 발음 입력 | 뜻 제시 → 읽기 입력(로마자→가나 변환 또는 일본어 자판) | 히라가나 기준. 힌트 사용 시 "어려움" 고정, 오답은 "다시" 고정 |

- B의 오답은 반드시 규칙으로 생성한다(무작위 단어 금지). N5는 소리 변형(탁음·반탁음·촉음·요음·장음·순서 바꾸기), N4 이상은 "같은 품사·한자 또는 분야 태그를 공유하는 다른 단어의 읽기" 2개 + 소리 변형 1개.
- B는 그 단어를 A 또는 C에서 최소 1회 맞힌 뒤에만 낸다(첫 노출 금지). 유효 오답이 3개 미만이면 B 제외.
- 급수별 기본 비중: N5 A2·B1·C1, N4~N3 A2·B1·C2, N2~N1 A1·B1·C2. 설정에서 0~3으로 조정.
- 후보 유형(미정): 표기 고르기, 문맥 규정, 바꿔 말하기, 한자→뜻 고르기, 뜻→한자 고르기. 객관식은 보조이고 뼈대는 회상·산출형이라는 원칙.

### 1-4. 세션 규칙
오늘 기한이 된 복습 카드 전부 + 신규 N개(기본 5, 설정 1~20)를 섞어서 출제. 세션 안에서 "다시/어려움"이 된 카드는 10분 뒤 재출제(대기 화면에 남은 시간 표시, 바로 보기 가능).

### 1-5. 개발 단계 (10장)
1. N5 50개 + 음성 + 화면 뼈대, 유형 A만 — 완료
2. 유형 C — 완료
3. FSRS 연결, 복습+신규 혼합, 세션 내 재출제 — 완료
4. 유형 B — 완료
5. Dexie 저장, 백업 내보내기/불러오기 — 완료
6. PWA·배포, 진도·설정 화면, 급수별 비중 — 완료
7. N4~N1 단어장, 추가 목소리, 급수별 분리 로딩 — 진행 중 (구조·목소리 2종·N5 700·N4 700·N4+ 오답 규칙 완료, N3~N1 남음)
8. 목표 설정·레벨 테스트·어휘 완주 계획 — 설계 메모만 있음
9. Capacitor 포장·스토어 출시 준비 — 미착수

## 2. 현재까지 진행 상황 (사실 위주)

### 2-1. 기술 스택과 규모
- React 19 + Vite 8 + TypeScript 6, ts-fsrs 5.4(스케줄링), Dexie 4(IndexedDB), wanakana 5.3(로마자→가나). 테스트는 vitest, 린트는 oxlint.
- 소스 약 2,800줄(TS/TSX, 테스트 포함). 테스트 8파일 46개 통과. 타입 검사·린트·빌드 통과.
- 배포: GitHub Actions가 push마다 테스트→빌드→GitHub Pages 배포. 서비스 워커는 화면 파일은 네트워크 우선, 음성 파일은 캐시 우선(요청한 파일만 저장).
- 개발용 파이썬 스크립트(앱에 포함되지 않음): 단어 초안 합치기, JMdict 대조 검증, Google Cloud TTS 음성 생성. 인증 키는 프로젝트 밖에 두고 경로만 .env로 읽는다.

### 2-2. 모듈 구조
```
src/
  types.ts, config.ts
  data/      words.ts(급수별 동적 import), words_n5.json, words_n4.json
  logic/     reading.ts(정규화·판정), distractors.ts(오답 생성)
  learning/  scheduler.ts(FSRS), session.ts(세션 구성), progress.ts(학습 상태 캐시),
             settings.ts, stats.ts, backup.ts
  platform/  storage.ts(Dexie), audio.ts(mp3 재생+Web Speech 폴백), file.ts(파일 입출력), pwa.ts
  screens/   Home, Onboarding, Present, QuestionA/B/C, Feedback, Waiting, Done, Progress, Settings
  App.tsx    화면 전환과 상태 연결
```
- 규칙: 저장소·음성·파일 같은 기기 기능은 platform/ 모듈로만 접근(화면 코드에서 브라우저 API 직접 호출 금지). Capacitor 전환 시 이 모듈만 교체한다는 계획.
- logic/·learning/은 순수 함수 위주로 짜서 테스트가 가능하게 했다.

### 2-3. 핵심 동작 수치
- FSRS: ts-fsrs 기본 파라미터, 학습 단계·재학습 단계 각 10분 1단계. 새 카드에서 다시=10분, 어려움=15분, 보통≈2일, 쉬움≈8일.
- "정착" 판정: 복습 상태이고 안정도(stability) 21일 이상.
- 진도 화면 정답률 등급: JLPT 성적표 참고정보처럼 67% 이상 A, 34% 이상 B, 그 미만 C.
- 학습 기록: 단어별 FSRS 카드 + 리뷰 로그(날짜, 유형, 판정, 평가, 소요 ms). JSON 백업(구조 버전 1) 내보내기/불러오기.
- 설정: 급수, 최초 실행 여부, 하루 신규 수, 급수별 유형 비중, 입력 방식, 목소리.

### 2-4. 단어장 제작 파이프라인
1. AI가 100개 단위로 초안 JSON 작성(표기·읽기·뜻·예문·예문 읽기·예문 뜻·품사·분야 태그·한자음).
2. 후보가 기존 급수의 표기·읽기와 겹치지 않는지 미리 검사.
3. merge_draft.py: 혼동 포인트(confusion) 태그 자동 계산, 급수·id 부여, 중복 검사.
4. verify_readings.py: JMdict(eng-common 3.6.2) 사전과 대조해 표기+읽기 조합이 실제로 존재하는지 확인. id 형식, 급수 간 중복, 예문 읽기가 가나만인지, 예문이 。로 끝나는지도 검사. 불일치는 자동 수정하지 않고 보고만 한다.
5. gen_audio.py: 목소리 2종(ja-JP-Chirp3-HD-Charon 남성, ja-JP-Neural2-B 여성)으로 단어 읽기 mp3와 예문 mp3 생성. 있는 파일은 건너뜀.
6. 테스트·빌드·커밋·푸시(자동 배포).

## 3. 현재까지 제작 완료한 결과물

### 3-1. 앱 기능 (배포본에서 동작)
- 최초 실행 목소리 선택(들어보기 가능), 홈 급수 선택(N5·N4 준비됨, N3~N1은 "준비 중"), 오늘 복습/신규 수 표시.
- 신규 단어 제시 화면(1초 뒤 발음 자동 재생, 예문 듣기 버튼), 문제 3유형, 피드백(정답/오답, 틀린 지점 안내, 버튼마다 다음 복습 간격 표시), 대기 화면, 세션 종료 화면(정답률, 내일 예정 수).
- 진도 화면(급수별 학습·정착 수, 정답률 등급), 설정 화면(신규 수, 급수별 유형 비중, 입력 방식, 목소리, 백업 내보내기/불러오기/초기화 2단계 확인).
- PWA 설치 가능, 오프라인에서는 이미 받은 화면·음성만 동작.

### 3-2. 콘텐츠
| 급수 | 단어 수 | 가타카나 단어 | 한자음 표시 | 혼동 태그 있는 단어 | 음성 파일 | 용량 |
|---|---|---|---|---|---|---|
| N5 | 700 | 56 | 181 | 335 | 2,800 (2목소리 × 단어·예문) | 31MB |
| N4 | 700 | 48 | 255 | 415 | 2,800 | 32MB |

- 읽기 검증 결과: 1,400개 모두 JMdict와 일치(불일치 0, 사전에 없음 0).
- JMdict "common" 목록에만 대조하기 때문에 자주 쓰지만 common 표기가 아닌 단어는 다른 단어로 바꿨다: N5에서 良い→いい, お酒→酒, ごめんなさい→失礼, おじさん·おばさん→男の子·女の子. N4에서 もうすぐ→打つ, お見舞い→見舞い, 応接間→洋服, お陰→料金, お子さん→画家, 入学式→歩道, お寺→家賃, お客さん→職業.
- 단어 선정 근거: JLPT 공식 어휘 목록은 없으므로, 구 시험 급수 어휘표와 교재 어휘를 참고해 AI가 선정. 출처 표기는 "AI 생성, 비공식".

### 3-3. 읽기 고르기(B) 오답 생성 규칙의 실제 결과 (N4)
- 후보 조건: 같은 품사, 읽기가 다름, 모라(음절) 수 차이 1 이하, 한자 공유 또는 분야 태그 공유.
- 점수: 한자 공유 3, 공유 태그 1씩, 길이 같음 2, 끝 모라 같음 1. 높은 순, 같으면 id 순이라 결과가 항상 같다.
- 예: 入院 → たいいん(退院)·にゅうがく(入学)·にゆういん(요음 변형) / 以上 → いない(以内)·いがい(以外)·いじよう / 召し上がる → さしあげる·もうしあげる·めじあがる.
- N4 700개 중 698개가 출제 가능, 668개는 다른 단어 오답 2개 확보. 약한 짝도 있다(貿易 → 出席·翻訳: 분야 태그 "work"만 공유).

### 3-4. 조사 문서
- docs/jlpt_exam_format.md: 급수별 시험 과목·시간·문항 수, 문자·어휘 문항 형식(공식 문제예 기준), 채점 방식, 공식 어휘 목록 부재, 앱 설계 시사점(유형 대응, 급수별 오답 규칙, 후보 유형, 비중, 통계 표시).
- 로마자 입력 규칙 조사: 일본어 IME 방식을 따르기로 결정(헵번·훈령식 자음 허용, 장음은 가나 철자대로, 예외 변환 추가 안 함). 네이버·구글·애플·MS 키보드 비교 후 "로마자→히라가나 변환만" 필요하다고 확인.

## 4. 앞으로의 계획 (개발자가 확정한 순서)

1. ~~N4 이상 읽기 고르기 오답 규칙~~ — 완료(2026-10-12)
2. N3 단어장 700개 — 같은 파이프라인. 초안을 합치기 전에 사전 검사만 먼저 하는 스크립트를 정식으로 추가 예정
3. 8단계 목표 설정·레벨 테스트·어휘 완주 계획 (아래 설계 메모)
4. N2·N1 단어장
5. 9단계 Capacitor 포장·스토어 출시 준비 (앱 이름에 "JLPT" 상표 사용 여부 확인 포함)
6. 후순위: 후보 문제 유형, 이미지 카드, 한자 분해

### 8단계 설계 메모 (아직 구현 전, 검토 대상)
- 최초 실행 흐름: 목표 급수 → 현재 수준(자기 신고 또는 레벨 테스트, 건너뛰기 가능) → 시험일 또는 학습 기간 → 하루 가능 시간 → 목소리.
- 레벨 테스트: 낮은 급수부터 급수당 20~25문항 적응형. 정답률이 떨어지면 중단. 읽기 고르기 + 일부 발음 입력. 객관식에 "모르겠음"을 4지선다와 분리해 아래에 둔다. 시간 제한 없음, 설정에서 재응시 가능.
- 채점: 답한 문항은 찍기 보정(맞은 수 − 틀린 수 ÷ 3), 모르겠음은 0. 틀림과 모르겠음은 따로 기록. 결과는 "N2 어휘 중 아는 비율"로 표현하고 급수 수준을 단정하지 않는다.
- 테스트 결과는 출발점일 뿐: 안다고 판정된 급수 단어는 "빠른 확인 모드"(읽기 고르기 한 문제, 맞히면 긴 간격 복습 상태로, 틀리면 신규로).
- 완주 계획: 하루 신규 = 남은 단어 ÷ 남은 날, 매일 재계산. 시험일이 있으면 신규 투입은 시험 2~3주 전에 종료. 예상 소요 시간은 범위로 표시(복습은 신규의 5~8배, 카드당 약 7초 가정) 후 첫 주 실측으로 재계산. 진도 화면에 계획 대비 앞섬/뒤처짐 표시.
- 테스트 없이 가는 표준 루트: N5부터 목표 급수까지 순서대로, 급수마다 "이 급수는 안다" 자기 신고로 건너뛰기.
- 이 앱은 어휘만 다루므로 "합격 커리큘럼"이 아니라 "어휘 완주 계획"으로 부른다.

## 5. 개발자가 스스로 인지한 약점·위험

1. **단어 수 대비 실제 급수 어휘량**: 흔히 인용되는 어휘 규모는 N5 약 800, N4 약 1,500(누적), N3 약 3,700(누적), N2 약 6,000(누적), N1 약 10,000(누적)이다. 급수당 700개 계획은 N5·N4에는 적절하지만 N3 이상에서는 범위의 일부만 다루게 된다. 급수당 목표 수를 늘릴지, "핵심 700개 + 확장" 구조로 갈지 결정이 필요하다.
2. **단어 선정과 급수 배정이 AI 판단**: 공식 목록이 없고 사람 검수도 없다. 일부 단어는 급수가 한 단계 어긋날 수 있다. 뜻·예문의 자연스러움도 원어민 검수가 없다.
3. **JMdict common 전용 검증의 부작용**: お寺·お客さん·お子さん처럼 자주 쓰는 お~ 형태와 入学式 같은 복합어가 "사전에 없음"으로 걸려 다른 단어로 대체됐다. 검증 정책을 완화(전체 JMdict 사용, 또는 お~ 접두 형태는 기본형으로 대조)할지 검토 여지가 있다.
4. **예문 음성의 한자 오독 가능성**: 예문 mp3는 한자 문장을 그대로 TTS에 넣어 억양을 자연스럽게 했다. 복수 읽기 한자(明日, 家 등)를 잘못 읽은 파일이 있을 수 있으나 전수 청취 검수는 하지 않았다.
5. **신규 단어 출제 순서**: 단어장 파일 순서대로 신규를 뽑는다. N4는 초안 묶음 단위로 50음순이라 以上·以下·以内·以外처럼 비슷한 단어가 연달아 나온다. 빈도순이나 분야 섞기 같은 순서 정책이 없다.
6. **FSRS 기본 파라미터 사용**: 개인화(옵티마이저)는 없다. 뜻 회상(A)에서 "어려움"도 정답으로 쳐서 B 출제 조건을 충족시키는 것이 적절한지 검토 여지.
7. **실사용 검증 부재**: 개발자가 아직 매일 쓰는 단계가 아니다. 입력 속도, 대기 화면 체감, 글자 크기 등 UX는 브라우저 자동 점검만 거쳤다.
8. **음성 용량**: 급수당 약 32MB(목소리 2종). N1까지 가면 약 160MB. 웹에서는 요청한 파일만 받으므로 문제없지만, 앱 포장 시 급수별 분할 내려받기 설계가 필요하다.
9. **학습 기록 크기**: 리뷰 로그를 단어별로 무제한 누적한다. 수천 단어·수년 사용 시 백업 JSON이 커진다.
10. **법적 확인 미완**: Google Cloud TTS 생성 음성의 앱 내 재배포 조건을 공식 약관에서 아직 확인하지 않았다(스토어 출시 전 확인 예정). JMdict(CC BY-SA)는 개발 시 검증에만 쓰고 앱에 포함하지 않는다.
11. **다른 단어 오답의 약한 짝**: 태그만 공유하는 경우(貿易→出席) 시험 오답으로서 그럴듯함이 떨어진다. 태그 체계가 비교적 거칠다(basic·daily 같은 포괄 태그).

## 6. 작업 규칙 (CLAUDE.md 요약, 검토 시 전제)

- 한 번에 한 단계만 구현하고, 요청받지 않은 다음 단계 기능은 만들지 않는다.
- 라이브러리는 설계서에 명시된 것만 쓴다(추가 시 허락 필요).
- 문제 유형은 A/B/C 세 가지만. 객관식 오답은 규칙 생성, 무작위 금지.
- 입력형 판정은 읽기(히라가나) 기준, 객관식은 선택지 동일성. 자동 판정 오답은 "다시" 고정.
- 저장소·음성·파일 입출력은 별도 모듈. 화면에서 브라우저 API 직접 호출 금지.
- 인증 키는 환경 변수로만. 런타임 외부 호출 금지.
- 모든 설명은 한국어, 전문용어에 한 줄 풀이.

## 7. 검토 요청 사항

아래 질문에 답해 주되, 근거(연구·시험 형식·구현상의 이유)를 함께 적어 주면 좋다. 우선순위가 높은 순서로 배열했다.

1. **콘텐츠 규모 전략**: 급수당 700개로 N1까지 가는 계획이 타당한가? §5-1을 고려해 급수별 목표 수를 어떻게 잡는 것이 좋은가? N3 시작 전에 결정해야 한다.
2. **8단계 설계(레벨 테스트·완주 계획)**: 적응형 문항 수, "모르겠음" 분리 배치, 찍기 보정식, "아는 비율"로 표현하는 방식, 하루 신규 재계산 규칙, 예상 시간 가정(복습 5~8배, 카드당 7초)에 대해 문제점이나 더 나은 방법이 있는가?
3. **문제 유형 비중과 B 출제 조건**: 급수별 기본 비중(N5 A2·B1·C1 → N1 A1·B1·C2)과 "A/C에서 1회 맞힌 뒤 B" 조건이 학습 효과 면에서 적절한가? N5에서도 다른 단어 오답을 섞어야 하는가?
4. **오답 생성 규칙의 품질**: N4 이상 규칙(§3-3)의 조건·점수 체계에서 개선할 점은? 태그 체계를 어떻게 정리하면 좋은가?
5. **단어장 검증 정책**: JMdict common 전용 대조를 유지할지, 완화할지(§5-3). 급수 배정의 신뢰도를 높일 현실적인 방법(공개 빈도 자료 활용 등)이 있는가?
6. **FSRS 설정**: 학습 단계 10분 1단계, 재학습 10분, 정착 기준 21일, "어려움=정답 취급"이 적절한가? 개인화 없이 기본 파라미터로 충분한가?
7. **신규 출제 순서**: 파일 순서 대신 어떤 순서(빈도, 분야 섞기, 비슷한 단어 간격 두기)가 좋은가?
8. **구조와 유지보수**: 코딩 경험이 없는 1인 개발자가 AI 도구로 유지보수하기에 현재 모듈 구조·테스트 범위가 충분한가? Capacitor 전환을 위해 지금 미리 바꿔 둘 것이 있는가?
9. **빠진 것**: 위 계획에 빠져 있지만 어휘 학습 앱에 꼭 필요하다고 보는 기능이나, 반대로 빼는 것이 나은 기능이 있는가?
